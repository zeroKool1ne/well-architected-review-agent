What it does

Two AI phases, one human gate.

An architecture diagram goes in, pillar findings come out — with a human confirmation in the middle.

PHASE 1 — EXTRACT (AI)        HUMAN GATE        PHASE 2 — REVIEW (AI)

  Upload → Extraction Agent → Human confirms → Pillar Agents ×3 → Findings
Every finding cites a best practice and a page number you can look up.

Measurement 2 — the one that changed the design

Telling a model not to hallucinate does not work.

"Never write that something is missing, disabled or unencrypted because the diagram is silent about it."
— in the system prompt, verbatim

With that instruction in place, the deliberately flawless test diagram still drew findings about:

  • missing mTLS
  • a single availability zone — on a diagram that names no zone
  • absent CloudFront

Strengthening the wording made it worse.

5
findings on a diagram whose correct answer is zero
A model that wants to be useful will find something. Instruction competes with that pull — and loses.
This is the most quotable slide. Pause after the punch line.

Measurement 3

One search reaches one pillar and stops.

"the workload is deployed across multiple availability zones"
  unfiltered →  reliability, 3 of 3
                the cost of cross-zone traffic never appears

"backups of the database"
  unfiltered →  reliability, 3 of 3
                whether they are encrypted is never asked
Filtering per pillar does not produce better passages. It forces a perspective that would otherwise never be taken.
This is why three specialists instead of one generalist. The numbers are on slide 12.
Consequence 3

Three specialists, one factory.

Security

Public buckets, IAM scope, encryption, secrets handling

Cost Optimisation

Always-on compute, oversized storage tiers, idle resources

Reliability

Single points of failure, retries, decoupling, backups

search_pillars(pillar="security")   ← same code
search_pillars(pillar="cost")       ← different system prompt
search_pillars(pillar="reliability")← different metadata filter

They run in parallel. A supervisor merges, deduplicates and ranks what comes back.

Routing is code, not a model. Models judge. Code decides what runs.
If asked why not an LLM router: a reviewer that sometimes forgets a pillar is worse than one that always runs all three.

Trade-offs taken knowingly

The limit — found two days ago

Isometric diagrams break it completely.

Exported from Arcentry, generated from this project's own Terraform plan. The ground truth comes from infrastructure code.

boxes found
100%
services named
0%
edges invented
98%

The labels degrade too: drift-check read as diff-check.

It is an excellent reader of horizontal text and a poor reader of pictures. Once the text stops being horizontal, the reading goes too.
This is the honest answer to "does it work on real customer diagrams". It depends on the style, and here is the measurement.
What happened next is the point

Extraction collapsed. The review said nothing.

Extraction   0% services, 98% edges invented
    ↓
Review       4 findings proposed
    ↓
Verifier     4 rejected
    ↓
Output       "No findings"

All four were inferences from silence:

  • "Lack of authentication"
  • "Single Availability Zone deployment"
  • two × "Potential cost savings…"

None of it is in the diagram.

The parts fail independently. The system becomes useless before it becomes wrong.
If you only land one point in the whole talk, land this one.
Honestly

What is still wrong.

  • Clean diagrams still draw one to three false positives per run.
  • Verification sometimes rejects a real finding — 3.0 of 4 instead of 3.4.
  • Pillar attribution drifts: missing backups are sometimes filed under cost.
  • Results vary between runs despite temperature 0. Every number here is a mean.

Next

  • Check pillar attribution the way findings are checked — structurally, not by instruction.
  • Messy, hand-drawn diagrams in the test set.
  • Corrected graphs are the start of an evaluation set that grows by being used.
The gate is not a limitation to engineer away. It is where the system earns trust.
Ending on limitations is deliberate. It is what makes the rest believable.
